LLM API Basics 📝

-- notes for myself, keep it simple --

1. What even IS an LLM API?

Simple analogy: Imagine texting a super-smart friend. You type a message → they read it → they text back. The "API" is just the phone line that carries your text to them and their reply back to you.

Technical: The LLM API is an HTTP endpoint you send a request to (your message + settings), and it returns a JSON response (the model's reply). No "friend" — it's a stateless server. Every time you call it, you must resend the WHOLE conversation, because it has no memory of before.

POST https://api.anthropic.com/v1/messages Body: { model, messages, max_tokens, temperature... }

2. Chat Completions (the endpoint)

Simple analogy: Like handing a whole chat history (the full WhatsApp thread) to a smart friend and saying "read all this, now what should I say next?" — they don't remember your last chat, so you re-send everything, every time.

Technical: "Chat completion" = you send an array of past messages (the conversation so far), and the model returns the next message that would logically come after it — this is literally called "completing" the chat.

3. Roles: system / user / assistant

Simple analogy: Think of a movie script:

  • Director's note (before scene starts) = system
  • Actor A's line = user
  • Actor B's reply = assistant

Technical:

system — sets behavior/personality/rules for the WHOLE conversation.
e.g. "You are a strict math tutor. Never give the direct answer."

user — what the human typed. e.g. "What is 2+2?"

assistant — what the model replied. e.g. "Try adding step by step!"

Every request = array like:

[ {role: "system", content: "You are a pirate."}, {role: "user", content: "Hi!"}, {role: "assistant", content: "Arrr, hello!"}, {role: "user", content: "How are you?"} ]

^ this whole thing gets sent EVERY single time!

4. Temperature

Simple analogy: Like a spice level dial 🌶️ for a chef. Low spice = same safe, predictable dish every time. High spice = chef gets creative/wild, different result each time.

Technical: Temperature controls randomness in word choice (0 to 1, sometimes up to 2).

  • temperature = 0 → same, most-likely, predictable answer every time (good for math, code, facts)
  • temperature = 1 → more variety, creative, less predictable (good for stories, brainstorming)

Rule of thumb: facts → low temp | creativity → high temp

5. max_tokens

Simple analogy: Like telling someone "you only get 100 words to answer" — a word-count limit for the reply.

Technical: max_tokens = the max number of tokens (roughly ¾ of a word each) the model is ALLOWED to generate in its reply. If the answer needs more space than that, it gets cut off mid-sentence.

max_tokens: 1000 → model can write up to ~750 words, then stops

Doesn't affect input size — only how long the OUTPUT can be.

6. Streaming

Simple analogy: Difference between:

  • Non-streaming = waiting for someone to finish writing a whole letter, then handing it to you all at once ✉️
  • Streaming = watching someone type a text message live, word by word, as it appears 💬

Technical: With stream: true, the API sends the response in small chunks (tokens) as they're generated, instead of waiting for the full completion. Great for chat UIs — feels instant instead of a long loading spinner.

stream: true → response arrives as: "The" "capital" "of" "France" "is" "Paris" ...(one chunk at a time)

✔ system = rules | user = you | assistant = model ✔ temperature = randomness dial | max_tokens = reply length cap ✔ streaming = live typing vs wait-for-whole-thing
