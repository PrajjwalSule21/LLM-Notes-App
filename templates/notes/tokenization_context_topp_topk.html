Tokenization, Context Window, top_p & top_k 📝

-- part 2 of my LLM API notes --

1. Tokenization

Simple analogy: Imagine you can't read whole sentences — you can only read them if they're chopped into small Lego pieces. Before the model can "think," it must break your sentence into these small pieces (tokens).

Technical: Tokenization = splitting text into small chunks (tokens) — not always whole words, sometimes pieces of words. The model doesn't see letters or words directly, it sees a list of token IDs (numbers).

"unbelievable" → ["un", "believ", "able"] (3 tokens) "Hi!" → ["Hi", "!"] (2 tokens)

Rule of thumb: 1 token ≈ ¾ of an English word ~100 tokens ≈ 75 words

Why care? Both max_tokens (reply limit) AND API pricing are based on token count, not word count or character count.

2. Context Window

Simple analogy: Like a whiteboard of a fixed size 🧑‍🏫. You can keep writing on it, but once it's full, the oldest stuff at the top has to be erased to make room for new stuff. The model can only "see" what fits on the board at once.

Technical: The context window is the MAXIMUM number of tokens (input + output combined) the model can handle in one request — the entire conversation history, system prompt, your new message, AND the reply it generates, all have to fit inside this limit.

Context window = 200,000 tokens → system prompt + all past messages + new message + max_tokens(reply) must together be ≤ 200,000

If your chat gets too long, old messages must be dropped/summarized — the model literally can't "remember" what doesn't fit on the whiteboard.

3. top_p (nucleus sampling)

Simple analogy: Imagine a chef picking the next ingredient not from ALL ingredients in the kitchen, but only from the top ones that together make up 90% of what's usually good — ignoring the weird rarely-used ones.

Technical: top_p = the model looks at all possible next-word probabilities, sorts them highest to lowest, and only considers words from the smallest group whose probabilities add up to p (e.g. 0.9 = top 90% probability mass). The rest are thrown away before picking.

Next word options: "cat"(40%) "dog"(35%) "car"(15%) "kite"(5%) "zebra"(5%) top_p = 0.9 → only considers "cat", "dog", "car" (sums to 90%) "kite" and "zebra" are excluded from being picked

top_p = 1.0 → considers everything (no cutoff) top_p = 0.5 → very narrow, safe, boring choices only

4. top_k

Simple analogy: Like a chef who only picks from a fixed shortlist of top 5 ingredients, no matter how good or bad each one is — a fixed COUNT limit, not a percentage.

Technical: top_k = only consider the top K most likely next tokens (a fixed number), then pick among just those.

Next word options ranked: "cat" "dog" "car" "kite" "zebra" "moon" ... top_k = 3 → only "cat", "dog", "car" are considered (top 3, no matter their %)

top_p vs top_k — quick comparison

top_ptop_k
Cutoff type% of probability massfixed count of words

Often used TOGETHER with temperature to control randomness — many APIs recommend tweaking only ONE of temperature/top_p at a time, not both.

✔ tokenization = chopping text into Lego-piece chunks ✔ context window = size of the whiteboard (input+output limit) ✔ top_p = pick from top X% probability pool ✔ top_k = pick from fixed top-K word list
