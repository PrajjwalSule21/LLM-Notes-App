Prompt Engineering Fundamentals 📝

-- zero-shot, few-shot, system prompt design + all other techniques --

1. What is "Prompt Engineering"?

Simple analogy: Like giving instructions to a new intern on day 1. Vague instructions ("do the report") = messy result. Clear instructions with examples ("here's last month's report as a sample, follow this exact format") = good result. Prompt engineering = getting good at writing those instructions.

Technical: Prompt engineering = the practice of designing the input text (prompt) to reliably steer the model toward the output you want — without changing the model itself, only the wording/structure/examples you give it.

2. Zero-shot prompting

Simple analogy: Asking the intern to do a task with ZERO examples — "translate this sentence to French" — no sample translation given. You're trusting they already know how, from general knowledge.

Technical: Zero-shot = you give the model ONLY the instruction/question, no examples of input→output pairs. Works because the model already learned the task pattern during training.

Prompt: "Classify the sentiment of this review as Positive/Negative/Neutral: 'The food was cold and the service was slow.'" → no examples shown, model just does it directly

Good for: simple, common tasks the model has clearly "seen" before (translation, summarizing, basic classification)

3. Few-shot prompting

Simple analogy: Now you give the intern 2-3 SAMPLE examples first — "here's how I labeled the last 3 reviews, now label this new one the same way." They copy the pattern instead of guessing.

Technical: Few-shot = you include a handful of example input→output pairs INSIDE the prompt, before the real question, so the model can pattern-match the exact format/style/logic you want.

Prompt: "Review: 'Amazing pasta!' → Positive Review: 'Waiter was rude.' → Negative Review: 'It was okay, nothing special.' → Neutral Review: 'The food was cold and the service was slow.' → ?" → model follows the exact pattern shown, outputs: Negative

Good for: tricky formats, specific style/tone, edge cases zero-shot gets wrong

Zero-shot vs Few-shot:

Zero-shotFew-shot
Examples given02-5 (usually)
Prompt lengthshortlonger (uses more tokens)
Reliabilityok for easy/common tasksmuch more consistent for niche/custom formats

4. System Prompt Design

Simple analogy: Remember the movie-script idea — the system prompt is the director's note read ONCE before filming starts, setting the tone, character, and rules for the entire scene. The actor (model) follows that mood for every line after.

Technical: The system prompt is a special instruction set at the START of the conversation (role: "system") that shapes the model's behavior for the WHOLE session — persona, tone, constraints, output format — separate from the actual user questions that follow.

system: "You are a senior Python code reviewer. Always point out bugs first, then suggest improvements. Keep responses under 100 words. Never write full rewritten code, only bullet-point feedback." user: "def add(a,b): return a+b" → model replies as that reviewer persona, in that format, every single time

Good system prompt design = be specific about:

  • Role/persona — "You are a ___"
  • Tone — formal, casual, blunt, friendly
  • Constraints — length limits, what NOT to do
  • Output format — bullet points, JSON, table, plain text
  • Edge case handling — what to do if unsure / info missing

Vague system prompt = "Be helpful." → generic, inconsistent behavior Specific system prompt = clear role + tone + format + rules → consistent behavior

5. Chain-of-Thought (CoT) prompting

Simple analogy: Asking someone to "show their working" in a maths exam instead of just writing the final answer — forcing step-by-step reasoning reduces silly mistakes.

Technical: You ask the model to reason through intermediate steps before giving the final answer, instead of jumping straight to it. Big accuracy boost on math/logic tasks.

Prompt: "A shop had 23 apples, sold 8, then got 15 more. How many now? Think step by step before giving the final answer." → "23 - 8 = 15. 15 + 15 = 30. Final answer: 30"

6. Zero-shot CoT

Simple analogy: The magic phrase "let's think step by step" said to ANY problem, with zero examples — like a teacher's generic hint that works for almost every question.

Technical: Combine zero-shot with a simple trigger phrase like "Let's think step by step" — no examples needed, just this one line unlocks step-by-step reasoning.

Prompt: "If a train travels 60km in 40 min, what's its speed in km/h? Let's think step by step."

7. Self-Consistency

Simple analogy: Asking 5 different people to solve the same puzzle independently, then going with whatever answer MOST of them agree on — majority vote beats one guess.

Technical: Run the SAME CoT prompt multiple times (with some randomness/temperature), collect multiple reasoning paths + answers, and pick the most frequent final answer. More reliable than a single CoT pass.

Run prompt 5 times → answers: [42, 42, 41, 42, 42] → majority vote = 42 (final answer)

8. Tree of Thoughts (ToT)

Simple analogy: Like exploring a maze by trying multiple paths at each fork, backtracking from dead ends, instead of committing to just one path from the start.

Technical: The model explores MULTIPLE reasoning branches at each step (like a decision tree), evaluates which branches look promising, and can backtrack — useful for complex planning/puzzle-solving where a single CoT chain can get stuck.

Step 1: generate 3 possible next moves Step 2: evaluate each ("promising" / "dead end") Step 3: expand only the promising ones, repeat

9. ReAct (Reason + Act)

Simple analogy: Like a detective who alternates between THINKING ("what should I check next?") and ACTING (going to check it, e.g. searching a database), using each new clue to guide the next thought.

Technical: The model alternates between Reasoning (thinking what to do) and Acting (calling a tool/API/search), using the tool's result to inform the next reasoning step. This is the core pattern behind most AI agents and tool-use.

Thought: I need today's weather to answer this. Action: call weather_api("Jabalpur") Observation: "32°C, clear sky" Thought: Now I can answer. Answer: "It's 32°C and clear in Jabalpur today."

10. Role / Persona Prompting

Simple analogy: Telling someone "act like a strict exam-checker" before giving them your essay — they nitpick harder than if you just said "check this."

Technical: Assign the model a specific persona/expertise ("You are a senior security auditor") to bias its vocabulary, depth, and focus toward that role's perspective. Often done via system prompt, but can also be inline in the user message.

"Act as a skeptical venture capitalist. Review this pitch and find every weakness an investor would find."

11. Least-to-Most Prompting

Simple analogy: Like breaking a big scary homework assignment into small sub-tasks and solving the easiest one first, then using that to solve the next.

Technical: Break a complex problem into a sequence of simpler sub-problems, solve them in order, and feed each answer into solving the next — good for multi-step problems that overwhelm a single CoT pass.

Q: "How many total wheels on 3 cars and 2 bikes?" Step 1: wheels on 3 cars = 12 Step 2: wheels on 2 bikes = 4 Step 3: total = 12 + 4 = 16

12. Generated Knowledge Prompting

Simple analogy: Asking someone to first recall everything they know about a topic on scratch paper, THEN answer the actual question using those notes — priming the brain before the real task.

Technical: First prompt the model to generate relevant facts/knowledge about the topic, then feed those generated facts back in as context for the actual question — improves accuracy on knowledge-heavy questions.

Step 1: "List 5 facts about how vaccines work." Step 2: "Using those facts, explain why 2 doses are often needed."

13. Step-Back Prompting

Simple analogy: Before answering a tricky specific question, first ask a bigger, more general question — like zooming out on a map before zooming into a street.

Technical: Ask the model to first answer a more abstract/general version of the question, then use that general understanding to answer the specific original question — reduces reasoning errors on tricky specifics.

Original Q: "What was the temperature in Paris on July 4th, 1854?" Step-back Q: "What general historical weather records exist for Paris in the 1850s?" → then answer the original using that broader context

14. Self-Refine / Reflexion

Simple analogy: Writing a first draft of an essay, then re-reading it yourself and rewriting the weak parts — instead of submitting the very first version.

Technical: The model generates an answer, then is prompted to critique its own output and produce an improved version — can be looped multiple times. Also called Reflexion when the critique is stored as "lessons" for future attempts.

Step 1: model writes an answer Step 2: "Review your answer above. Find mistakes or weak points." Step 3: "Now rewrite the answer, fixing those issues."

15. Chain-of-Verification (CoVe)

Simple analogy: After writing an answer, fact-checking yourself by asking a list of "is this actually true?" questions before finalizing — like proofreading a report against your sources.

Technical: Model drafts an initial answer, then generates verification questions to check facts in that answer, answers them independently, and revises the original answer based on any contradictions found — reduces hallucination.

Draft: "The Eiffel Tower was built in 1887 and is 400m tall." Verify Q1: "What year was the Eiffel Tower built?" → 1887-1889 Verify Q2: "What is the Eiffel Tower's height?" → ~330m → Revised: "...built 1887-1889, is about 330m tall."

16. Prompt Chaining

Simple analogy: An assembly line — one worker's output becomes the next worker's input, instead of one person trying to do the entire car build alone.

Technical: Break a big task into a sequence of separate prompts/API calls, where each step's output feeds into the next step's input — more reliable than cramming everything into one giant prompt.

Call 1: "Summarize this 10-page report." Call 2: "Using that summary, write 3 action items." Call 3: "Turn those action items into a Slack message."

17. Structured Output Prompting (delimiters, XML/JSON tags)

Simple analogy: Giving someone a fill-in-the-blanks form instead of a blank sheet of paper — they can't wander off-format because the boxes are already drawn.

Technical: Explicitly instruct (and often show an example of) the exact output structure — JSON schema, XML tags, markdown table — so the response is easy to parse programmatically. Widely used when the output feeds into other code.

"Respond ONLY in this JSON format: { "name": string, "sentiment": "positive"|"negative"|"neutral" } No extra text before or after the JSON."

18. Retrieval-Augmented Prompting (RAG-style)

Simple analogy: Open-book exam vs closed-book exam — instead of relying purely on memory, you hand the model the exact reference pages ("here's the doc, answer using only this") right inside the prompt.

Technical: You retrieve relevant documents (from a database/search) and paste the relevant chunks INTO the prompt as context, then ask the question — grounds the answer in real, current, or private data instead of the model's memory alone.

Context: [paste 3 relevant paragraphs from company policy doc] Question: "What is our refund window per this policy?" → answer must be based only on the pasted context

19. Meta Prompting / Automatic Prompt Engineering (APE)

Simple analogy: Asking a professional resume-writer to write YOUR resume instead of writing it yourself — here, you ask the model to write or improve the prompt itself.

Technical: Use the LLM to generate or optimize prompts for a given task — e.g. generate 10 candidate prompt variations, test them, keep the best one. Automates prompt design instead of hand-crafting it.

"I want a prompt that makes you summarize articles in exactly 3 bullet points, in a neutral tone. Write the best possible system prompt for this."

20. Negative / Contrastive Prompting

Simple analogy: Telling a new employee not just what to do, but also what mistakes past employees made — "don't do X, don't do Y" — sharpens understanding by contrast.

Technical: Explicitly state what the model should NOT do (avoid certain words/formats/behaviors), sometimes alongside a "bad example" vs "good example" pair, to sharpen the boundary of acceptable output.

"Write a product description. Do NOT use the words 'amazing' or 'revolutionary'. Bad: 'This amazing revolutionary blender changes everything!' Good: 'This blender crushes ice in seconds and cleans itself.'"
